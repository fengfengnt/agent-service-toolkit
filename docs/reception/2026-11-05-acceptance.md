# 小鹤接待 Agent 实施与联合验收

执行范围：C0共享契约、B1—B6独立Collaborator业务与管理端、A1—A7接待服务、F1—F6门户，以及J1隔离联合验收。正式部署、真实短信、付费模型和正式知识库未包含在本次执行中。

## 已实现

- 接待分流和三方向专业答疑，18项基础Skill及知识查询预留；先答疑再邀请、暂缓后不催促、明确切换、草稿按方向续接及多份先选择。
- 小鹤保存分轮草稿；聊天/卡片/总览共用资料与版本。明确确认当前汇总后才正式提交；未知结果按原键核对，避免重复建申请。
- 同用户同公司复用档案，新需求独立申请；修改原申请保留经理、进度及历史版本。组织服务申请和入驻申请分别确认。
- 供应商可选私有材料，原始流上传、受权下载和运营反向读取；不将材料原文送入模型。
- “我的进展”按公司/组织分组，显示各次需求、实际分派经理、定级和公开记录；未知值不编造，审核通过与入驻完成分别显示。
- Java新增 `yudao-module-collaborator` 和7张 `co_` 表，使用 `collaboratorId`；SSO仅作只读权威身份核验。没有迁移原member/supplier/CRM业务数据或修改其表结构。

| 场景 | 实际结果 |
| --- | --- |
| 同用户两公司、同公司两次采购需求和一个供应商需求 | 同公司共用主体，各申请独立；加组织后共3个主体、5条正式服务申请 |

| 可选供应商PDF | 实际MinIO写入、用户受权下载、Java反向下载字节一致；另一用户下载403 |
| 后台维护经理和进度 | 真实运营服务更新后，门户读到“隔离生态经理”“人工评估A”和公开沟通记录；其他申请仍未分派 |
| 后台成功响应丢失 | Java先受理再断开响应；AI保持未确定，查询原键恢复；没有重复申请 |

| 身份和租户隔离 | 来源租户2、业务租户9；跨system拒绝；另一用户进展为空，旧账号CSRF与新Cookie混用403 |
| Native门户新需求 | 原受权主体预填，独立汇总确认，显示实际受理回执；进展新增一条，MySQL服务申请为6条 |

J1发现并修复了实际PG死锁：同一事务连续更新Run会触发session复合外键检查，原认证用户worker先持有conversation、页面先持有session，产生循环等待。现在统一session→conversation→Run；并发用例先失败后通过，原身份/执行期限/撤销语义回归通过。最终J1日志没有deadlock；不以自动重试掩盖。

## 不能由本次结论代替的验收

Java在专用HTTP测试容器中桥接MockMvc，执行实际控制器、过滤器、事务和MySQL；中心权威适配器、运营权限与经理目录是受控替身，未启动完整生产后台配置。Python使用测试装配复用产品路由/图/worker；Node Runtime与浏览器是真实运行。IdP/claim和抽取模型是受控替身；原浏览器PKCE/OIDC/Cookie逻辑照常执行。浏览器仅对本次临时测试证书放行，Node和HTTP客户端使用明确测试CA验证。
