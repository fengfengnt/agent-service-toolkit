# 小鹤标准 Skill、DeepAgents 接入与 workflow 精简设计

日期：2026-11-11。

状态：2026-11-11 用户以“定稿”批准整体设计；独立审阅已完成。接续制定实施计划，当前不开始产品编码、安装依赖、迁移或部署。

## 1. 目的与已确认决策

在现有 LangGraph 的业务节点内接入 DeepAgents，使接待、采购、社群组织、供应商四个 Agent 能按标准格式使用 Skill，并能为后续 subagent 分配独立的技能和工具。留资引导不再受固定三轮分支限制，可通过 Skill 重新组织现有字段、解释、追问和 form；涉及接口或界面的变化允许配合开发发布。

决策细节集中保存在[设计地图](../../../.scratch/standard-skills-deepagents-20261111/map.md)及各决策票，不将设计者的技术选择写成用户逐项指定。

用户已确认：

- 业务节点内使用 DeepAgents，保留外层 LangGraph。
- 首版支持系统已有字段的自由组合；不要求仅改 Markdown 就完成所有功能变化。
- 节点及 subagent 显式绑定候选 Skill；先依据可信身份与权限筛选，再按说明选择，按需加载正文和资源。
- 一轮可组合多份已授权 Skill；同一草稿由当前留资 Skill 推进，其他 Skill 辅助答疑或分析。
- 首版 subagent 只返回处理结果，主业务 Agent 统一调用工具保存和提交；以后按需显式开放特定 subagent 的写入权限。
- 外部 Skill 由 Codex 检查依赖并绑定，执行能力通过授权工具接入；缺少必要能力时适配后再启用。
- 旧草稿保留字段要求和资料；新轮次可用新版引导，根据已有资料及可核对的完成记录重新判断待办；在途动作、重试和已出站提交保持原版本及原请求。
- 系统权限、字段规则、提交条件和真实结果始终有效；配置冲突由维护者处理，无法判定的运行时冲突暂停受影响动作并保留草稿。
- 首版包括四 Agent、三份留资及十八份答疑 Skill、必要的前后端适配，以及只读 subagent 的配置和隔离验证。
- 后续实施允许更新 `langchain`、`langgraph` 及必要的相关依赖，以得到兼容版本组合；本轮不实际升级。

## 2. Goals / Non-goals / Anti-goals

### Goals

- 二十一份资源成为符合 Agent Skills 规范的可导入技能包，具备准确的适用说明及按需加载能力。
- 可由 Codex 配置哪个业务节点、哪个 subagent 使用哪些技能及工具，不把权限判断交给技能文字。
- 在相同字段和后端能力下，新增、合并、调整留资引导步骤时，无需扩写一组对应的 workflow 分支。
- 保留现有身份隔离、真实业务状态、确认、幂等、恢复、过期清理及旧客户端兼容。
- 将主流程的重复编排收敛，明确 Skill、工具、执行快照及前端表单各自的职责。

### Non-goals

- 本轮编码、依赖安装、锁文件修改、数据迁移、部署和真实模型／短信调用。
- 首版新增字段类型、任意字段设计器、在线 Skill 编辑器、技能市场或自动下载安装第三方依赖。
- 首版通用 Shell／脚本执行、动态生成可写 subagent、具体生产子任务、跨轮长任务及子任务专用进度界面。
- 改造其他 toolkit 示例、独立重建聊天／身份／任务服务，或替换现有正式业务后端。

### Anti-goals

- 只补 frontmatter，正文仍一次性全量注入，并宣称已实现标准 Skill 使用。
- workflow 节点变少，却把权限、必填、确认和业务结果判断全部挪入提示词。
- DeepAgents 的 checkpoint、TODO 或模型记忆成为第二份草稿／正式申请数据库。
- 为精简流程删除旧执行器，导致已执行一半的旧请求无法恢复。

## 4. Approaches：已讨论的路线

| 路线 | 取舍与结果 |
| --- | --- |
| 现有 LangGraph 加自行实现的标准 Skill 加载／选择机制 | 对现有业务适配直接，但后续 subagent、资源发现等需继续自行实现；未选。 |
| 在现有业务节点中接入 DeepAgents | 复用其 Skill 和 subagent 能力，保留现有业务权威；需要依赖兼容、状态恢复和工具授权适配。用户已选择。 |

不把本次设计扩大为整套业务迁入另一个 Agent 服务。以下 workflow 精简、状态接入及投影版本是设计者基于所选路线提出的技术方案，随本文整体审阅。

## 5. workflow 如何精简

保留外层客服图的接收、等待、取消与恢复职责。每个业务 Agent 的自定义 workflow 收敛为三个职责节点：

| 节点 | 职责 |
| --- | --- |
| `prepare_context` | 从可信状态构建身份、方向、字段快照、已填资料、完成记录和本轮技能／工具集合；固定版本，识别按钮等确定性输入。 |
| `business_agent` | 调用该角色的 DeepAgents 图，选择 Skill，答疑、组织 form、追问、调用获授权业务工具或只读 subagent；需要用户输入时结束本轮。 |
| `finalize` | 根据真实工具回执校验并生成现有 `AgentOutcome`、关键提示及等待输入标记；处理交接，不重复执行业务工具。 |

`understand`、`decide`、普通 `answer` 以及 `answer_details`／`answer_auth` 的模型编排合并到 `business_agent`。`collect`、`save`、`summary`、`submit`、`resume`、`new`、`progress` 等独立路由不再各占一个语义分支；对应能力继续存在为授权工具和共用业务服务。组织方向的兼容入口保持真实行为，不因迁移重新建立独立入驻申请。

设计目标为四个业务定义各三个职责节点；DeepAgents 内部仍有模型、工具和 subagent 节点，因此这不是整个运行图只有十二个节点的承诺，也不承诺模型调用或延迟一定减少。

| 可以收敛的内容 | 仍须由程序保证的内容 |
| --- | --- |
| 固定轮次、引导顺序、答疑与留资组合、同义意图到业务动作的编排 | 身份／租户／系统隔离、可用字段、必填、资料证据、版本和并发修订 |
| 多份回答节点、专业方向的重复路由表 | 工具授权、提交确认、幂等、未知结果核对、真实回执及取消后的写入禁止 |
| 每新增一段引导就增加节点和路由 | 进度及快照持久化、保留未保存输入、过期清理及旧请求恢复 |

新运行时允许受控工具调用后继续模型循环，故不直接放宽旧 `dsl-v1` 编译器的限制。使用单独标识的新运行时（本文建议 `deepagent-v1`）和新的业务节点装配；旧运行时继续按原校验和原快照恢复。不得只删除旧图的“写入后禁止模型调用”检查就接入 DeepAgents。

新运行时由固定工厂装配三个职责节点，宿主配置只描述角色与能力绑定；不再实现另一套通用 workflow DSL。已校验的按钮、form 保存等确定性请求在 `business_agent` 中可直接走对应受控工具，不为它们额外要求一次模型决定或把按钮语义交给 Skill 改写。

方向交接继续由外层现有协调机制执行，保留每轮最多一次交接、明确切换才转向及各方向草稿独立接续的边界。DeepAgents 返回交接请求，不直接修改另一角色的草稿或无限循环调用其他业务 Agent。

## 6. 标准 Skill 包与节点绑定

以 Agent Skills 开放规范为文件格式：`SKILL.md` 含 `name`、`description` frontmatter，正文写适用场景、步骤、输入／输出要求、工具使用条件及异常交接；引用资源按需读取。目录名称与 `name` 一致，采用全局不重复的短横线命名，例如 `buyer-lead-capture`、`buyer-security`、`supplier-security`，避免现有多处 `security` 目录产生歧义。

资源统一组织在 `resources/xiaohe/skills/<skill-name>/`。主文件保持跨宿主可读，不要求每份外部 Skill 添加小鹤专用必填 frontmatter。已有角色字段配置可作为留资包中的引用资源，由现有严格类型解析后形成字段快照；它是业务工具的结构化依据，不是模型可改写的说明。

节点装配配置在宿主侧表达：角色、节点、允许的 Skill、当前流程 Skill、工具及 subagent 绑定。复用现有 workflow 资源装载、校验和内容快照机制，不引入通用插件注册服务；具体配置键由实施者按既有模型风格制定。旧 `buyer.requirements` 等 ID 到新名称的映射只用于兼容旧资源和回执，不将映射伪装成标准字段。

执行顺序：

1. 检查绑定存在、名称唯一、资源路径合法、必要依赖可用。
2. 根据服务端可信身份、方向及权限筛选本轮可见 Skill 和工具；业务方向不等于用户身份或权限。
3. 只将筛选后的名称与 description 供模型发现；选中后按需读取正文及资源。
4. 当前留资流程按节点配置明确绑定，已有草稿的活动留资 Skill 作为已选技能由程序确定性载入，避免模型漏选；其他适用 Skill 按需组合。不依赖未核对版本的 pin API。
5. 每次实际读取和工具调用仍检查范围，不能靠隐藏目录名称实现权限隔离。

DeepAgents 的技能来源通常指向包含技能子目录的父路径，因此不能简单把单个 `SKILL.md` 路径传给它。由适配器将本轮允许的不可变资源投影为受限的虚拟技能目录；未授权包的目录、正文及引用资源均不可读取。首版不向模型开放整个仓库文件系统。

导入时保留来源、版本或内容指纹并核对许可证、格式、引用路径和所需能力。脚本、工具依赖通过已授权业务工具适配；缺少必要能力的 Skill 不进入可用集合。导入不触发通用 Shell、依赖安装或任意外部地址访问。

## 7. 留资步骤、字段与表单组合

将“字段规则”与“引导步骤／表单展示组合”分开：前者决定允许的数据及正式提交要求，继续按草稿固定；后者属于每轮 Skill 的交互规范，可在下一轮更新。

当前 FieldPolicy 内保存的旧 `rounds` 留作旧客户端和旧执行器兼容；新运行时不以其序号限制引导，不把新的展示分组写回旧字段快照。继续复用已有字段、类型、枚举和校验器，不新增任意字段或条件语言。

Skill 可描述“先澄清采购诉求，再展示公司与联系人，必要时补充系统和预算”，也可增加解释、确认或整理步骤。模型通过受控表单工具提出已有字段的组合；服务端从该草稿字段快照生成实际标签、类型、选项、必填和限制，拒绝未知字段及越权字段。

自由组合只涵盖当前角色、草稿规则及接口允许编辑的已有字段。历史记录中仅为兼容而保留的字段继续保留，不能仅因它们存在于后台资料中就自动开放编辑，也不能因为当前 form 未展示而被删除。

引导进度至少能表示当前流程 Skill、适用版本、当前待办及已完成事项。非字段步骤的完成记录需关联本轮已发布的解释、用户回复或真实工具回执；模型单独声称“已解释／已确认”不构成不可核对的完成依据。新增步骤没有对应证据时保持未完成。具体存储复用现有草稿和 Command 的关联机制，不另建任务系统。

同一用户可以同时在 form 填写和聊天；已填写信息可复用，未展示字段不得被客户端全量空值覆盖；清空仍需明确意图。切换角色、选择多份草稿、复用唯一草稿及已受理申请修改继续走现有业务规则。

## 8. 主业务 Agent、subagent 与工具

首版只装配显式配置的自定义 subagent；避免默认通用 subagent 自动继承主 Agent 的写入工具。自定义 subagent 的技能目录、只读工具和必要上下文单独指定，不继承整个父对话、身份凭据或所有资料。

固定版源码表明，“isolated”主要隔离对话，默认 `task` 仍可能传入并合并自定义 state；仅写 `tools=[]` 也不会移除默认文件写工具。首版采用 `CompiledSubAgent` 的明确输入／输出包装：只传已授权的只读任务快照，只接受校验后的结果消息／结构化结果，不允许 child 返回业务 state 更新或 `Command.update`。可信业务上下文由服务端工具闭包或受控运行上下文提供，不放入可被 child 合并覆盖的模型 state。

主 Agent 与每个 child 均显式限定文件工具为必要的只读技能读取能力，backend 仅提供授权快照，无 Shell 执行能力；关闭默认 general-purpose 子 Agent，child 也不再装配委派能力。禁用方式以固定版公开 profile／中间件 API 为准，并以“工具实际不可调用”的测试确认，不依赖提示词或空工具列表。

子任务首次范围为同步、有限、只读计算：可用测试中的资料整理／完整性检查任务验证，不新增正式业务子任务或多层递归委派。子任务返回有边界的结构化结果，主业务 Agent 校验后使用；子任务不能生成可信的保存／受理状态。任务结果不能被当成用户本轮的字段原文或提交同意。

工具按职责复用现有业务服务：读取当前资料与进展、准备／恢复草稿、投影 form、保存明确资料、确认并提交、请求方向交接。工具清单中的名称可以适配现有函数，不要求按此清单再造一套服务。

每个写工具必须：

- 从服务端上下文取得主体、Command、WriteFence 和版本，不接受模型传入的用户身份或权限替代它们。
- 校验角色、草稿归属、允许字段、原文证据、修订及该动作的前置条件；匿名用户只走现有认证，登录完成不自动提交。
- 复用当前确认证据语义：语境中的“好的／可以”可以确认，否定／暂缓／未满足条件不能确认；按钮仍校验用户实际查看的汇总版本。
- 主 Agent 对正式提交提供结构化的语义确认候选，服务端将其绑定到可信的当前 Command、原始用户消息、角色及最终资料版本后形成确认证据；单独一次 submit 工具调用或 child 的判断不等于用户已确认。
- 同轮修改并提交使用最终已校验的字段快照；必要时将修改与提交作为现有共用提交服务的一次业务准备，不让工具链绕过修订一致性。
- 使用稳定业务动作记录及原提交键；不能仅依赖模型生成的 tool_call_id 去重。
- 数据库事务只覆盖必要的读取／写入，不跨模型或网络等待持锁；出站前后复查写栅栏与取消状态。

工具执行后的新模型调用只用于选择后续动作或表达，不能修改已发生的事实。写入后模型超时，结果必须可从已持久化回执恢复并生成确定性提示，不能为重新生成话术而重做业务。

未来给某个 subagent 开放写入，必须显式配置并接入相同工具校验；属于后续扩展，不因父 Agent 授权、Skill 的 allowed-tools 或正文指令而自动获得。

## 9. Skill 组合与冲突

允许当前留资 Skill 与答疑／分析 Skill 在同一轮组合。当前流程的引导归属唯一，辅助 Skill 不改写字段规则、保存条件及提交确认；程序通过工具边界落实，不能仅在提示词中声明优先级。

绑定、名称、依赖和可验证配置冲突在启用前拒绝；两份流程技能同时争用同一草稿时交由维护者修正装配。用户的业务意图不清才向用户澄清，不能让普通用户裁定内部配置。

运行中无法判定的说明冲突暂停受影响动作、保留草稿及已完成结果；其他已完成业务不撤销、不重做。不能保证自动识别所有自然语言矛盾，必须保留真实模型语义评测和越权尝试用例。

## 10. 版本、checkpoint 与恢复

业务权威继续是现有 Run、Command、草稿、规则快照和正式提交记录。DeepAgents checkpoint 只恢复内部消息、技能加载、工具循环及只读子任务，不决定“资料已保存／申请已受理”。

| 对象 | 版本和恢复规则 |
| --- | --- |
| 草稿字段规则 | 创建／显式兼容绑定后固定；旧草稿字段要求不自动变化。 |
| Skill 包、引用资源、绑定及工具配置 | 在新用户 Command 开始时选定并形成不可变内容快照；同轮恢复不读取后来覆盖的同名目录。 |
| 当前流程与完成记录 | 下一轮按新版已发布引导重新计算待办；复用资料与可核对完成事项，不靠旧步骤编号匹配。 |
| 执行中的工具与正式提交 | 原载荷、原动作身份、原提交键、原规则及 Skill 快照；未知结果沿原请求查询。 |

复用已有 PostgreSQL checkpoint 基础设施，通过显式的运行时适配给 DeepAgents 提供 saver。由于现有业务子图关闭 checkpoint，不能假定嵌入后自动拥有持久恢复。原生内部消息状态与外层 `AgentOutcome` 状态需要明确输入／输出转换，不直接混用两个 state schema。

本方案选择独立调用 DeepAgents 根图，通过服务端派生的独立 `thread_id` 隔离每个 Command、业务角色及当前执行实例，根 `checkpoint_ns` 保持默认。不复制外层配置的内部 task／checkpoint 字段，不依赖手写非空 namespace 隔离两个根图；当前 LangGraph 固定版根调用会重置它。

内部线程引用记录在该 Command 的服务端执行信息中。同一执行实例重试恢复原引用；更换 attempt／ownership 时沿用现有互斥及停止检查，需要隔离时创建新物理线程并从可信快照与回执恢复，避免旧 worker 覆盖新 checkpoint。物理线程变化不得改变业务动作键。首次调用才追加该用户消息，恢复通过原生继续方式推进已有 checkpoint，不重复追加原输入。

主 Agent 需要用户输入时，本轮返回现有等待结果，由最外层 `await_input` 接续新 Command；首版不在 DeepAgents 内再建立一套面向用户的长期 interrupt。表单、认证与普通用户澄清均沿用现有输入入口。subagent 的同步内部状态不能另行请求用户输入。

首版不启用会产生内层 HITL interrupt 的工具／中间件。若出现意外内层暂停，适配器保留 checkpoint 并返回明确的受控错误，不将未完成图当作正常答复结束 Command，也不误用外层用户回复去恢复另一个 interrupt。未来需要内层 HITL 时再设计两层等待的显式映射。

首次执行写工具前记录动作身份、内容指纹与执行状态；完成后记录可信回执。恢复时先查业务记录：已完成返回原结果，结果未知沿原请求核对，未开始才执行。checkpoint 与外部 API 不具备天然原子性，不能以 checkpoint 已保存为恰好执行一次的证明。

新增的内部 checkpoint 线程必须纳入现有取消、过期和访客正文清理枚举；同一内部线程下 subagent 命名空间一起清理。缺少原技能包、绑定或运行时版本时保留任务并报告不可恢复，不能静默切换最新版。

## 11. 前后端投影

现有 `leadPolicy` v1 保持兼容：未声明、未知版本、重复头继续既有行为；旧客户端的 `rounds`、固定 step 和保存／确认请求不能被悄悄替换。

设计者建议通过同一读取接口的显式能力版本 `X-Xiaohe-Lead-Policy: 2` 提供新版投影；响应使用 `leadPolicy.version = 2`，区分固定字段规则与本轮引导／form 组合。仅在客户端明确声明时返回新版结构，v1 调用保持原形状。

新版投影需覆盖有效字段规则版本、交互／Skill 版本、当前 form 标识、草稿 revision、要展示的已有字段组合、当前待办和可用动作。展示组合和内部流程完成记录不能让客户端修改字段门槛；敏感身份、工具权限、系统提示和完整 checkpoint 不投影给前端。

form 标识与版本由服务器签发并校验，防止旧面板操作错套新组合。保存仍调用原业务保存逻辑；若需附带 form／交互版本，用显式兼容扩展或独立版本化请求，不给旧请求强加新必填属性。正式提交仍以后端最终资料快照及确认证据为准。

门户复用现有字段组件展示新组合，不建设任意页面生成器；保留当前 owner／会话／方向／草稿匹配、面板去重、未保存输入与焦点保护。新版组合到达但用户正在编辑时先保留本地输入，再合并服务端状态或提示核对，不静默替换。

旧门户继续使用旧分组投影及集中表单，新增引导不能要求它完成不可见的新必填字段。新门户连接旧后端时缺少 v2 投影，回退已有展示；后端仍可通过聊天及旧 form 接续。

子任务和技能调用的内部流式消息不直接作为用户聊天内容，沿用 AG-UI 内部消息过滤；关键提示、认证卡片、面板控制和受理结果由服务端真实状态生成。

普通答疑保留现有来源、一般建议及待确认口径，LLM 只能提供经过既有回答校验的自然文本候选；不能直接输出可执行面板指令或可信业务状态块。即使写工具已经成功，后续模型自由文本也不能替代、撤销或伪造服务端回执。

门户和可能涉及的 Java 接口适配形成独立交接；本轮仅设计，不跨工程修改正在进行的代码。

## 12. 依赖与能力验证

不得直接把浮动官方主文档的所有 API 当成已安装版本能力。选择固定 DeepAgents 发布版及兼容的 LangChain／LangGraph 组合，核对 `skills`、subagent 配置、禁用默认能力、checkpoint 和异步调用接口。

用户允许升级 `langchain`、`langgraph` 及必要关联包；保持仓库既有依赖发布时间冷却规则，除非后续有单独的明确例外。实现前做锁文件解析、导入和现有 Agent／运行时回归，不为维持旧依赖而自造另一套技能引擎。

根据[官方能力调研](../../../.scratch/standard-skills-deepagents-20261111/deepagents-research.md)，以 `deepagents==0.7.32` 为固定候选（2026-10-23 发布，符合当前十四天冷却规则）；其最低要求包括 `langchain>=1.4.7`、`langchain-core>=1.7.0`、`langsmith>=0.14.12`。现有 core 声明必须放宽，LangChain／LangSmith 锁内版本需更新。现有 LangGraph 锁为 `1.2.16`，目前未发现直接最低版本冲突；用户允许按验证需要更新，不强行升级无关包。

候选能力核对对应 DeepAgents 固定源码 `e85c6b98087861512d2c5240305e16cfac68a746`。允许实施时在满足既有发布策略的兼容版间选择，但更换候选须重新核对默认工具、subagent state 传递与 checkpoint 语义。完整传递依赖仍未解析，本文不声称已经解锁或通过导入／运行验证。

首版能力必须至少验证：受限 Skill 读取、自定义只读 subagent、主 Agent 写工具、异步工具错误传播、checkpoint 重试和调用结束行为。没有经过验证的库默认能力不进入生产装配。

## 13. 迁移、兼容与回退

1. 以已提交三方向留资实现为业务基线，冻结当前规则、确认证据和回执行为作为迁移对照。
2. 整理二十一份标准包和宿主绑定，保留旧技能 ID／旧 bundle 的读取与回执兼容；用内容快照而非覆盖目录支持历史恢复。
3. 增加新运行时及四角色共用装配，让新 Command 在明确切换后使用；执行中的旧 Command 继续旧运行时。旧 Run 等待的新 Command 可按现有选版边界接入新版，不重写在途 Run 及提交。
4. 表单投影 v2 与门户组合展示配套上线；旧客户端继续原规则。保存／提交业务服务与正式后台记录不重建。
5. 通过隔离验收后再单独申请发布；本文批准不等于部署、真实模型、短信或正式业务写入授权。

回退保留旧请求可执行代码及全部不可变快照。已有新运行时执行记录时，只将后续新请求切回兼容版本；不能回滚到无法读取新确认证据／执行信息的旧程序。已出站请求继续查询原结果，不能因回退重发新申请。

## 14. 验收与风险

| 验收主题 | 需要证明的行为 |
| --- | --- |
| 标准包 | 二十一份包通过格式及路径检查；名称无冲突；正文及资源按需读取；缺依赖时明确不可用。 |
| 节点与角色 | 四角色各用自己的技能／工具；接待不能获得专业写权限；模型猜测路径或工具名无法越权。 |
| 多 Skill | 同轮答疑加留资成功；辅助说明不能降低字段要求；冲突保留草稿且不误提交。 |
| form 自由组合 | 三步改四步、合并／重排已有字段无需新增固定路由；未知字段、旧 revision 和过期 form 被正确处理。 |
| 接续 | 旧草稿保留规则与资料，下一轮采用新版引导；非字段步骤有可核对完成依据，不重复索要已知信息。 |
| 主子职责 | 自定义 subagent 可独立加载授权 Skill 并返回结果；即使模型尝试，也无法保存／提交或继续委派。 |
| 提交 | 语境确认、同轮修改提交、按钮汇总、缺项、并发冲突和真实结果均保持当前业务契约。 |
| 恢复 | 工具执行前后崩溃、模型后续失败、结果未知、取消／过期及旧 worker 继续运行，均不重复受理或越权写入。 |
| 清理 | 新内部 checkpoint 及子任务资料随原会话／访客生命周期清理，不遗留正文。 |
| 前端兼容 | v1 不变、v2 配套展示、旧前端／旧后端组合可回退；未保存输入、角色隔离和可信面板标记保持。 |
| 工作流精简 | 新定义使用三个职责节点；业务要求与恢复覆盖仍存在，旧请求执行器不被删除。 |

先通过假模型、业务桩与独立临时数据库验证确定性边界，再在后续授权范围内开展真实模型语义评测及前后端组合验收。真实模型需评估技能漏选、互相矛盾的说明、幻造状态、表单组合稳定性、延迟和调用成本；节点减少不代表上述指标自动改善。

主要风险为依赖升级回归、自由引导漏步、技能说明误选、工具副作用后的模型失败、旧新执行快照不兼容及动态 form 覆盖本地输入。对应控制已分配给版本快照、权限工具、完成证据、稳定回执、兼容运行时和前端保护；本轮没有运行验证结果。
