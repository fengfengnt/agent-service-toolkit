# 小鹤内嵌 ChromaDB 知识库接入设计

日期：2026-11-11

状态：用户已批准；进入实施计划阶段

范围：接待、采购、社区组织、供应四个业务 Agent。

## 1. 已确认的需求与目的

- 中文名称使用“小鹤”，代码标识符保留 `xiaohe`。
- 知识量少，采用内嵌 ChromaDB，不增加独立知识库服务。
- Markdown 保留技能说明和基础兜底答复；业务知识由 ChromaDB 检索补充。
- 知识必须保留资料来源、版本、适用条件，并限制各 Agent 的访问范围。
- 用户已接受“修改文档 → 手动构建知识版本 → 重启 worker 生效”的维护方式。

用户可以在 Codex 开发对话中提供资料、提出修改，由开发助手维护源文件并执行已授权的构建。四个业务 Agent 首期只读知识；与它们聊天不构成知识入库或发布。更新运行环境时仍须明确目标环境，不由一句业务聊天自动触发部署。

## 2. Approaches：方案与选择

| 方案 | 优点 | 代价及结论 |
| --- | --- | --- |
| 独立 ChromaDB 服务，后端统一检索 | 集中管理索引，方便多个进程访问 | 增加容器与运维。曾推荐此方案，用户说明知识量很少后，选择内嵌方案。 |
| 现有 Agent 执行宿主内嵌 ChromaDB，离线构建独立版本目录 | 组件少，适合当前四个 Agent 的小规模资料 | 限定单个知识查询进程，严格分离构建目录和在线目录。用户选择此方案。 |

不再同时实现两种存储模式。若今后需要多个知识查询进程或其他系统直接访问，再另行设计服务化。

## 3. 当前实现与改动边界

- `src/agents/tools.py` 是模板 Agent 的 Chroma 示例，只返回拼接正文；不直接挂到小鹤回答节点。
- `scripts/create_chroma_db.py` 只导入 PDF/DOCX，默认删除旧库；本次不得沿用其覆盖在线索引的行为。
- 小鹤当前回答节点通过 `load_skill_materials` 读取绑定 Bundle 内的 Markdown，再调用 `compose_answer`。
- `WorkflowBundle.resources` 会进入 Bundle 摘要，整体快照存入 PostgreSQL `JSONB`，运行和部分草稿绑定固定 Bundle。
- 接待 Agent 的 `skills` 当前为空，不能只给三个专业 Agent 的技能检索加功能，就声称四个 Agent 均已支持。
- 现有 `KnowledgeQuery` 属于旧接待路径；本次接入当前 DSL 工作流，不扩展旧路径。
- 当前容器根文件系统只读，API 与 worker 分离，镜像未安装可选 `rag` 依赖。
- 实际调用链为 `RunWorker` → `ToolkitClient.stream_execution` → API 内部执行入口 → `build_graph` / Agent 回答节点。Agent 执行宿主是 API 进程，worker 是调度者；内嵌索引必须装配到 API，不能放在 worker 中。

预计涉及知识源与导入命令、Bundle 资源加载、API 执行宿主的检索依赖注入、回答资料与来源校验、配置/镜像/持久化挂载、维护文档及针对性测试。不改变路由、交接、表单采集、业务确认和提交规则。不覆盖工作区现有的其他任务修改。

## 4. 知识源与维护入口

采用独立的 `resources/xiaohe/knowledge/` 目录存放 UTF-8 Markdown，不把现有技能说明自动全部复制入库。`skills/` 继续承担技能发现、回答边界和无知识库时的基础资料。

每份知识文件含 YAML front matter 和正文，至少声明：

- `id`：稳定且唯一的资料 ID。
- `title`：资料标题。
- `source`：可对客展示的来源名称或公开地址；不放私有路径、凭据或内部管理地址。
- `conditions`：适用条件，无特别条件也须明确表达。
- `agents`：非空白名单，取值仅限四个实际 Agent ID；共享资料显式列出多个 Agent。
- `topics`：资料所属主题；专业主题引用现有技能 ID，通用接待资料使用固定的 `general` 主题。

入库校验重复 ID、未知 Agent、非法或不匹配的主题、缺失元数据、空正文、文件体积、路径越界及符号链接越界。正文和授权信息共同参加版本计算。原始文档作为知识的可审阅来源，Chroma 索引可重建。

首期只新增 Markdown 入库能力；不实现网页上传、业务聊天写库、自动监听目录、抓取网站或完整文档管理后台。PDF/DOCX 的既有示例保留，本次不扩展到新发布流程。

知识文件必须是用户提供或确认可对客的资料。模板和测试数据不作为真实公司政策发布，不根据模型生成内容自行补齐报价、案例、承诺或适用条件。

## 5. 内嵌检索怎样服务 Agent

在现有 Python 后端中增加小型检索模块，由 API 中实际执行 Agent 的宿主进程持有内嵌 Chroma 客户端，worker 不打开索引。Agent 不直接访问数据库，也不获得发布权限。不新增 HTTP、MCP 或其他对外检索 API。

回答节点先保留现有 Markdown 材料，再在可检索的答疑路径中补充知识命中。模型识别意图时仍使用现有技能说明，不能通过知识正文改变允许的技能、动作或 Agent 身份。

查询范围从可信的 `AgentFrame.agent_id`、绑定的 Bundle 和代码已校验的主题推导，禁止从用户原话或模型生成参数接受 Agent 身份、知识版本、目录、collection 或任意过滤器。

首期查询文本使用已校验主题的审定标题，不把用户原话、联系方式、公司字段、历史正文或附件发送给 Embedding 服务。专业 Agent 按当前已识别技能主题检索，并可读取显式授权的 `general` 资料。接待 Agent 在现有答疑路径中使用固定的通用接待查询词，仅检索授权给 `xiaohe-reception` 的 `general` 资料；不扩大其专业技能或改变交接路径。明确离题、固定开场、流程控制和业务写入路径不新增知识检索。

在数据库查询阶段应用 Agent 和主题过滤，并在返回后再次检查授权、版本、内容摘要及字段约束。默认拒绝未授权资料。设置有限结果数、文本长度和检索总时限；具体限值由实施者依据现有 `KnowledgeHit` / 回答限制确定并用小型评测校准，不把“排名第一”当作事实正确的证明。

返回材料沿用 `KnowledgeHit` 的正文、来源、版本、适用条件。需区分机器可校验的来源 ID 与可展示来源，避免重用或伪造引用。模型只能引用本次实际提供的材料；版本和条件随材料传入，系统在结构化回答/现有答复正文中保留可追溯依据，不仅依赖模型自行记住版本。

知识片段始终视为数据。不能用其指令改变权限、生成认证结果或执行表单提交。旧模板 `database_search` 不直接复用，因为它丢失元数据且没有 Agent 范围约束。

## 6. 不可变版本、Bundle 与索引目录

每次构建生成知识清单：规范化知识源及授权、分块参数、Embedding 模型标识/维度、索引格式标识和内容摘要。用确定性摘要作为知识版本；相同输入可以复用已验证的同版本产物。

将知识清单作为一个新的、可选的 `WorkflowBundle.resources` 条目，自动进入现有 Bundle 摘要并随快照持久化；不修改旧 Bundle 的摘要算法或强制给旧快照增加字段。清单同时承载检索所需的可信文档元数据及校验摘要，但不包含密钥。运行以自己绑定的 Bundle 找到知识版本，禁止读取一个全局可变的“最新版本”。

构建写入新的临时目录，校验完成、客户端关闭后，将完整产物发布到 `<knowledge_root>/<knowledge_version>/`；存在同名目录时验证一致性，拒绝覆盖或清空。完成标记只在验证成功后生成。修改或删除源文件通过新版本体现，不就地修改在线索引。

构建进程只写未发布的新目录，在线 API 执行宿主只查询已发布目录。Chroma 打开本地持久化库仍可能维护自身文件，因此 API 的专用持久化目录需要可写，不能宣称整个索引目录可按只读文件系统挂载。逻辑上禁止在线业务增删知识。worker 不挂载或打开 Chroma 目录。

一个运行重试或交接时继续使用原版本。已绑定旧 Bundle 的草稿按现有机制使用旧资料，不暗中迁移到新知识；无知识清单的旧 Bundle 完全保持现有 Markdown 行为。保留旧目录，不在首期加入自动清理任务。无法找到旧索引时降级到该 Bundle 自身的 Markdown，不切换到新版本。

限定单个知识查询宿主进程，即当前单进程 API；不能配置多个 Uvicorn workers 或 API 副本共享同一路径。部署和运维说明明确此限制，并提供实际可执行的排他保护。停止查询进程前不以运维脚本直接打开同一路径。备份优先保存源文件、清单及 Embedding 配置标识；复制持久化索引前停止 API 执行进程，避免不一致文件快照。

## 7. 构建、发布与回退操作

用户操作方式：

1. 在本项目的 Codex 对话中明确新增/修改/删除哪些知识，并提供内容、来源、适用条件和可访问的 Agent；也可以自行编辑 Markdown。
2. 开发助手或维护人员执行知识校验与构建，检查变更清单和检索样例。构建失败不影响在线版本，也不产生可用的新清单。
3. 构建产物和对应清单一起进入明确目标环境；按现有发布流程暂停 worker 的新调度并处理在途执行，再更新/重启 API 以加载新 Bundle 与知识目录，确认就绪后恢复 worker。不得让在途执行被切到新知识版本，失败重试仍读取原 Bundle。不能仅重启 worker 就忽略真正执行 Agent 的 API。
4. 新运行使用新发布版本；已有运行/绑定草稿继续使用原版本。回退时恢复此前资源包/镜像和知识版本，新运行重新绑定旧版本；不修改既有运行记录。

用户接受的“重启 worker 生效”是此前维护方式的简述；源码核查已纠正为重启 API 执行宿主并协调 worker 调度。实施文档必须说明实际发布步骤。知识少且更新不频繁，首期不实现在线热切换。

每次维护回执说明知识版本、变更文档、Agent 授权变化、验证结果及是否已经应用到目标环境。修改文档、构建成功、目标环境生效分别报告，不混为完成。

## 8. 配置、Embedding 与失败处理

复用现有 `rag` 可选依赖及 `langchain_openai`，不引入新的向量库或 Embedding 提供商抽象。运行配置需要知识根目录，以及明确的 Embedding endpoint、model 和凭据。Embedding 与聊天模型是独立能力，不假设当前聊天服务一定支持 Embedding，也不隐式切换模型或下载本地模型。

Embedding 模型标识及维度必须与构建清单一致；更换模型须构建新版本。凭据仅在私有环境变量中提供，不入源文件、清单、日志或 Git。没有实际可用配置时功能保持未启用，原有 Markdown 工作流照常运行。实施阶段提供配置示例；真实 Embedding 联通、费用及真实业务知识验收单独记录，不能用受控向量测试声称已通过。

失败或未命中时回到现有 Bundle 的 Markdown 资料。接待 Agent 没有技能 Markdown，因此保持其现有提示词约束及无依据时说明待确认的行为，不伪称它已有专业技能兜底。记录受限的内部状态，区分禁用、无命中、版本缺失、校验失败、超时和上游不可用，不泄露问题正文或秘密。

查询/Embedding 不能长时间阻塞异步 API 执行宿主；使用明确超时并限制并发，确保同一客户端操作和取消处理不会产生后台并发访问失控。实现方式由实施者选择既有异步/线程机制，不新增任务平台。

## 9. 验收标准

- 新增、修改、删除 Markdown 后构建新版本；源文件不经发布不会改变在线回答，旧版本不被覆盖。
- 非法元数据、路径越界、重复 ID、错误授权或不匹配的模型/维度被拒绝。
- 四个 Agent 均可在相应现有答疑路径获得明确授权的知识；接待通用资料独立验证，专业技能和路由不因接入而扩大。
- 查询前过滤及查询后复核共同防止跨 Agent、跨主题、跨版本资料进入模型；注入文本不能扩大权限，私密用户字段不进入 Embedding 请求。
- 同一运行重试、Agent 交接及旧草稿保持绑定知识版本；旧 Bundle、禁用、缺库、空结果、超时、损坏或错误版本时保持既有兜底行为。
- 来源 ID、可展示来源、版本和适用条件可追溯，模型编造的来源被拒绝。
- 使用真实嵌入式 Chroma 与确定性测试向量验证持久化、版本目录隔离和排他访问；单元测试不请求收费模型。
- 覆盖当前工作流和来源校验回归，校验容器持久化目录权限、可选依赖启用及 API/worker 资源版本一致性。没有运行的检查明确标注。

## 10. 非目标与实施者可决定事项

本次不做知识管理 UI、业务 Agent 自学习、自动业务事实审核、租户私有资料库、外部应用 API、多进程共享本地索引、在线热更新、自动旧版本删除或直接部署到任何环境。

初版只存可对客、按 Agent 授权的资料；不把用户上传附件、会话正文或申请表字段自动变成知识。

具体模块名、CLI 名、清单文件名、分块参数、结果上限和测试组织由实施者在不扩大范围的前提下确定。首次真实发布需要维护人员提供已确认知识及可用的 Embedding 配置；缺少时交付并验证技术能力，明确保持业务运行的知识检索未启用。
