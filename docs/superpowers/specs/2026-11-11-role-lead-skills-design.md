# 小鹤三方向留资 Skill 设计

日期：2026-11-11。

状态：2026-11-11 用户以“定稿”批准整体设计；独立审阅已完成。进入实施计划阶段，本文件不授权编码、迁移或部署。

后续授权：同日用户选择“本对话逐项实施”，按[实施计划](../plans/2026-11-11-role-lead-skills.md)开发与隔离测试。下文“本轮”指设计阶段，实施进展以计划及[验证记录](../../testing/xiaohe-lead-skills.md)为准；未授权正式迁移或部署。

## 1. 目的与已确认决策

把采购、组织机构、供应商的留资步骤、表单要求和沟通规范分别收敛为三份业务 Skill，复用共用执行机制，降低规则分散在提示词、Python 和门户组件中而产生的偏差。

用户已确认的业务决策以[设计地图](../../../.scratch/role-lead-skills-20261111/map.md)及其中链接的决策票为准，本文件将其组合成可实施的设计：

- 普通解释可自然表达；必填提示、提交告知和受理结果统一，不能省略或编造。
- 不新增或删减当前必填项，后续由产品经理确认字段需求。
- “好的”“可以”等口语可构成确认，以 LLM 结合上下文识别的提交意图为准，不要求固定句式。
- 资料满足当前必填要求且识别为同意提交时，直接提交，不强制先展示汇总再确认一次。
- 新草稿采用新版字段规则，已有草稿保留原字段要求与资料。
- 已有草稿从下一轮对话起采用已发布的新话术和交互规范，原字段要求不变；执行中的动作及已发出的提交按原版本、原内容和原请求处理。

具体目录、配置结构和兼容协议作为整体设计获批；设计批准与实际实施授权分开。

## 2. Approaches：方案比较与方向

| 方案 | 取舍 |
| --- | --- |
| 仅编写三份 Markdown，由 LLM 自行执行全部步骤 | 文档简单，但不能保证必填、资料一致性、幂等及真实结果；不满足关键提示和提交约束。 |
| 三个角色各自维护一套完整执行代码 | 隔离直观，但认证、提交和异常处理重复，容易出现只修一个角色的情况。 |
| 三份角色配置包＋共用交互规范＋共用执行机制 | 每份维护本角色差异，关键约束统一执行；沿用 LangGraph、Pydantic、现有草稿及业务后端。 |

用户已批准第三种方案的完整设计；三份角色 Skill 共用执行机制，不由三套独立 Agent 互相协商。

## 3. 范围

纳入：三份留资 Skill 的装配、字段与交互版本分离、关键提示、语义直接提交、Artifact 表单投影、旧草稿兼容与回归。

保持：现有认证／租户／系统隔离、真实业务接口、材料存储、授权校验、幂等及进展查询。合作与入驻仍使用已有统一申请，不恢复另一套入驻流程。

不纳入：新增必填内容、管理后台 Skill 编辑器、任意字段设计器、VIP 供应商独立 Agent、模型替换、知识库改造、运行时执行任意代码。本轮不实施或发布。

## 4. 当前代码事实与实际改造边界

- `resources/xiaohe/workflows/*.yaml` 定义资料分组、必填、节点及路由；`src/xiaohe/workflows/models.py`／`compiler.py` 校验与编译。
- `resources/xiaohe/skills/catalog.json` 与 `src/xiaohe/reception/skills.py` 当前用于答疑材料，不等同可执行留资流程。
- `src/xiaohe/agents/nodes.py`、`reception/flow.py`、`reception/organization.py` 仍有固定话术及兼容流程。
- `agents/contracts.py:ConfirmationEvidence`、`nodes.py:validate_confirmation_evidence` 和 `reception/submission.py:confirm_locked_draft` 当前绑定已展示汇总；提示词也排除部分短确认。本设计必须同时调整这些约束，不能只改提示词。
- `workflows/definitions.py:draft_definition` 已绑定历史 bundle，但还会投影部分必填要求；存量适配必须核对实际有效规则，不能简单认定历史规则完全不受后续逻辑影响。
- `workflows/store.py:bind_run_bundle` 固定执行 Run 的快照。新的用户 Command 可能继续同一等待输入的 Run，因此新交互规范不能只在创建新 Run 时选版。
- 门户 `frontend/src/chat/reception/fields.ts`、`ReceptionSummaryPanel.vue`、`presentation.ts` 含字段或提示口径；只修改 AI 提示词无法完成前后端统一。
- 另一项已批准的内嵌知识库设计保持独立：留资规则不作为知识证据入库，不由检索文档改变权限、字段或提交状态。

这些是设计核对时的实现事实；本文中的口语直接提交等新规则尚未在代码或生产生效。

## 5. 三份 Skill 与共用规范的组成

建议在本项目资源目录形成以下包结构；此处只说明目标，不创建这些产品资源：

```text
resources/xiaohe/lead-skills/
  common/policy.yaml
  buyer/SKILL.md
  buyer/policy.yaml
  organization/SKILL.md
  organization/policy.yaml
  supplier/SKILL.md
  supplier/policy.yaml
```

- 三个角色 Skill 的稳定 ID 建议为 `buyer.lead_capture`、`organization.lead_capture`、`supplier.lead_capture`。
- `SKILL.md` 负责本角色的业务目标、转化场景、解释方式、可选追问和示例，不重复维护完整字段与必填名单。
- 角色 `policy.yaml` 负责字段规则、资料分组、引导配置、对共用关键提示的引用及版本信息。
- 共用 `policy.yaml` 负责直接语义提交、认证分流、保存／提交／未知结果等交互规则和固定模板；不是第四个独立 Agent。
- 共用执行器只执行已注册的动作，不执行配置中的 Python／SQL、任意工具或任意外部地址。
- 流程 Skill 通过显式角色绑定装配，不混入原答疑 topic 列表，避免把内部流程要求当成公司知识向用户复述。

## 6. 资料规则与三角色差异

初版逐项复用当前已生效的字段定义、枚举、字段格式和存储归属，不借本次重构提高门槛。

| 方向 | 资料分组的业务侧重点 | 当前最低必填 |
| --- | --- | --- |
| 采购 | 企业背景；采购需求与联系方式；选填补充 | 企业名称、联系人、联系电话 |
| 组织机构 | 组织背景与渠道；服务需求与联系方式；选填补充 | 组织名称、会员规模、覆盖区域、线上渠道、联系人、联系电话 |
| 供应商 | 企业背景；产品与能力、联系方式；选填补充与附件 | 企业名称、联系人、联系电话 |

可执行字段清单仍以当前三份 YAML 和校验目录为来源；上表不是第二份配置。供应商附件仍为选填，不新增证照必交或联系电话格式门槛。

每项字段规则需能表达现有的字段 ID、显示名称、受支持类型、选项、说明、当前校验及资料分组。企业／组织公共资料与本次申请资料的存储归属保持，不能因整理 Skill 互相覆盖。

表单、LLM 的字段上下文、缺项计算和正式提交校验必须来自该草稿绑定的同一份有效规则。Skill 文本中的解释不能增加必填，模型输出不能修改字段定义。

Artifact 允许集中填写全部资料，分组用于组织和引导，不要求用户逐轮聊天。用户也可在聊天中提供或修改已支持的资料，由原文证据与校验机制回填；不猜填未提供的信息。

## 7. 交互流程

### 7.1 转化与草稿

1. 当前服务方向由现有可信对话状态确定，调用相应 Skill。方向不明时先澄清，不猜测角色。
2. 识别转化后先答疑。采购三个已展示快捷入口继续作为明确转化；其他表述由 LLM 结合上下文判断。
3. 会员直接准备本角色资料；访客复用既有认证流程，不把认证成功视为正式提交确认，不新增跨认证的无人值守自动提交。
4. 当前角色唯一未完成草稿可复用；多份时让用户选择，不新增重复草稿；切换方向保留各自资料。
5. 发出确定性的采集提示，让门户打开或重开对应 Artifact；普通咨询不反复强制打开。

### 7.2 保存与直接语义提交

- 保存资料不等于正式提交。用户单独查看汇总仍可用，但不是自然语言提交的强制前置步骤。
- LLM 负责识别提交语义；“好的”“可以”可在上下文中表示提交，不做词语黑名单或固定句式二次拦截。
- LLM 可在同轮识别字段补充／修改与提交。建议先校验并保存用户明确表达的改动，再按最新资料和绑定规则检查必填，齐备后直接提交；不因同轮带修改而一律要求再确认。
- 必填未齐时统一提示实际缺项，不调用正式提交接口。没有新的用户输入时，不因后台补充或规范升级自行提交。
- 身份、权限、当前角色、草稿归属和资料版本仍由服务端校验。确认所针对的资料与真正出站的资料必须一致。
- 如果模型判断后发生并发资料修改，返回冲突并展示当前状态，不静默换用新资料代替用户确认的内容。
- 已受理／受理中的原请求沿原提交核对；只有明确的新需求才创建另一项申请。

### 7.3 确认证据

按钮确认继续绑定用户实际核对的汇总与修订。自然语言直接提交采用独立的语义确认证据，绑定本轮用户消息、角色、草稿修订、采用的字段与交互版本，以及提交资料快照。

不得伪造“用户已看过汇总”的状态，也不得简单删除全部确认检查。直接语义路径可以从采集中进入提交，但仍要留下可核对的确认来源与不可变提交载荷。已有唯一性和提交键机制继续复用，重试不得生成另一份申请。

旧提交记录保留原含义。当前 summary_version 非空等历史约束与新证据的具体持久化方案交由实施计划落实；若需数据库变更，必须独立制定兼容迁移，不能用虚构汇总版本掩盖两种确认来源的差异。

## 8. 话术：自由表达与固定关键块

角色 Skill 可规范普通答疑的语气、篇幅和解释重点；模型不输出或改写业务成功状态，也不自行生成认证卡片、表单或系统通知。

关键块由服务端根据真实状态和草稿规则生成。模型的自然答复可与关键块同轮组合，关键块不能被覆盖、删掉或换成相反承诺。

| 场景 | 建议统一模板 | 使用条件 |
| --- | --- | --- |
| 开始填写 | 请在资料面板填写本次{方向}资料。 | 已准备对应草稿 |
| 必填缺项 | 正式提交还需：{实际缺项名称}。 | 系统计算确实缺项 |
| 草稿保存完成 | 本次资料已保存，尚未正式提交。 | 已收到保存成功结果 |
| 正在提交 | 正在提交本次资料。 | 已进入受控提交动作 |
| 结果待核实 | 正在核实提交结果，请稍后查询，无需重复提交。 | 尚无确定受理回执 |
| 已受理 | 本次需求已受理，可在“我的进展”查看状态。 | 真实业务回执已确认 |
| 明确失败 | 本次提交未完成。{可公开的处理提示} | 有明确错误；不把网络超时直接认定为拒绝 |

这些文本是已批准的模板设计，尚未上线。不得从“已受理”推导出已安排人工联系、已审核通过或已开通服务。

现有 `system_notice` 的“开始填写需求资料”是已交接的兼容性协议标记，初版保持稳定，不作为任意可改写的话术；新的可见解释可由模板生成。界面控制不得依赖模型自由答复文本。已有多语言能力保持，不新增语言平台。

## 9. 版本与恢复边界

| 对象 | 绑定时机 | 更新影响 |
| --- | --- | --- |
| 草稿字段规则 | 新草稿创建时 | 已有草稿不自动换字段／必填／校验要求 |
| 角色引导及共用交互规范 | 每轮新的用户 Command 开始时 | 已有草稿的后续轮次可用新版 |
| 本轮执行快照与回执 | 本轮选版并开始执行后 | 续跑与重试继续原版本，不在中途热换 |
| 已出站提交 | 准备提交载荷及稳定提交键时 | 原内容、原键查询与重试，不重建或改写 |

同轮必须记录角色 Skill、交互规范、字段规则和确认资料版本，记录不等于把内部 ID 或凭据暴露给 LLM。

不能只在新 Run 创建时更新交互版本：现有等待输入的 Run 会承接新 Command。实现须在用户轮次边界选版，同时保留 Run 外壳的恢复约束；不得为升级直接篡改正在执行的 Run.workflow_bundle_id。

引入 Skill 时，旧草稿以接入时实际生效并对用户展示的字段口径形成兼容绑定，保留已有字段和资料；不得把最新版字段覆盖进去，也不借此撤销此前已生效的业务要求。真正执行中的旧动作及出站提交保持原快照。

## 10. 前后端投影与兼容

共用规则和三份 Skill 在 AI 服务内解析为严格结构化模型。前端展示是服务端规则的投影，不再独立决定必填、字段分组或受理成功口径。

技术建议：现有接待读取接口支持显式能力声明 `X-Xiaohe-Lead-Policy: 1`。声明支持的新版门户可读取附带 `leadPolicy` 的投影，包含本次有效的角色、字段说明／类型／选项、字段规则版本、交互版本与关键提示。未声明的旧客户端继续接收原响应形状，不假设它能容忍额外字段。

该扩展仅用于门户直连的接待／表单读取，不改变现有 AG-UI viewVersion、Runtime 转发或正式提交请求。新门户在旧后端缺少投影时保留当前兼容展示；新后端不把旧客户端不能显示的新字段悄悄设为必填。首期字段完全沿用现有内容。

保存、确认按钮与进展仍走原授权 API；前端输入校验是用户提示，服务端才是正式校验依据。采集提示到达后等最新匹配草稿就绪再打开面板，按 owner／会话／消息去重，保留未保存输入及焦点。

门户 Agent 需单独实现规则消费、状态话术统一和去重行为；涉及 Java 正式业务契约时也单独交接。本文不授权跨工程编码。

## 11. 配置发布与受控能力

- 通过仓库文件维护与版本化发布，不允许业务聊天修改 Skill、字段门槛或已发布规范。
- 在当前支持的字段类型、资料分组和动作范围内修改配置；新增字段类型、工具、外部调用或新业务动作仍需开发和评审。
- 发布前验证角色绑定、字段合法性、分组引用、模板变量、版本引用和可执行动作。错误配置不得以默认最新规则替代旧草稿规则。
- 不引入 Python eval、任意脚本或用户自带工具地址。模型和检索资料只能提供内容或语义候选，不能提升权限。
- 只做版本选择与资源加载的机制规范，本设计不要求新增热更新服务、后台编辑器或新的运行进程。

## 12. 验收要求

1. 三角色各自加载正确 Skill；字段、表单、缺项及提交要求一致，无串角色资料。
2. 会员转化后先答疑再准备资料；访客认证；唯一草稿复用、多份选择；已有 Artifact 能按新提示重开。
3. “好的／可以”在确认提交语境下有效，在其他语境不误当提交；结果依据语义决策而非关键词。
4. 资料齐备且无已展示汇总时可直接语义提交；按钮路径仍验证真实汇总，不能伪造已查看证明。
5. 同轮修改后提交按最终已校验资料形成快照；缺项、非法值或并发版本变化不静默提交。
6. 保存、待核实、真实受理和明确失败各用正确固定提示；不存在无回执的成功承诺。
7. 新字段规则只影响新草稿；旧草稿字段不变，但在同一等待输入 Run 的新 Command 中可使用新交互规则。
8. 执行中规范更新、超时重试、响应丢失和受理核对不更换原版本／载荷／提交键，不重复受理。
9. 旧 API 客户端保持兼容；新版门户的能力声明、规则投影、状态显示和未保存输入保护通过组合测试。
10. 初次接入不得提高当前有效必填门槛或覆盖存量资料；历史提交仍可读取和查询。

确定性状态和真实数据库隔离测试与真实模型语义评测分开。真实模型评测、短信或业务写入须在后续授权范围内进行；当前设计阶段不执行。

## 13. 后续交付与设计者建议
